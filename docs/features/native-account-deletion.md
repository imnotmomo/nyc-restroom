## Scope and behavior

Account has a compact red Delete account action below Sign out, with native confirmation and verification through the existing Apple or Google identity. Open web finder is removed; Privacy and data use remains. Cancellation does not submit a deletion. UID/session guards prevent another account from being deleted, and success requires the exact confirmed server response.

A completed deletion removes Firebase Authentication and the account’s saved places, private notes/codes, shared codes, verification receipts and paired visit reports. Submitted public restroom locations and existing cleanliness ratings remain without their account ownership links. Other people’s data and contributions remain unchanged.

Public community listings retain their complete original venue details and dates without a write. Their stable IDs are randomly generated and their strict schema contains no account UID. Only the private submission-ownership receipt is removed. Existing ratings move atomically from `ratings/{uid}` to a separate Admin-only `anonymousRatings/{randomID}` record containing only the original valid stars and rating timestamp. No UID, UID hash or identity mapping is retained. Public rating count, sum, average and update time remain unchanged, even for an already missing or malformed summary. Any future aggregate repair must count both vote collections. A malformed own rating fails closed for administrative repair rather than copying private fields or inventing a rating.

## Backend and recovery

The existing Firestore Standard database is `(default)` in `nye-restroom`, with billing disabled. The isolated VPS service uses a dedicated least-privilege administrative credential outside Git and outside the main web process. Native clients POST only `{}` and a verified Firebase ID token to the fixed HTTPS endpoint; they cannot select a UID.

A private server-owned deletion lock blocks old clients and stale tokens from private access or authenticated writes after cleanup starts. Ownership receipts are gathered before UID-scoped recursive deletion. Public code/visit cleanup, listing unlinking and rating anonymization are processed under a renewable lease. The durable `data-deleted` phase is committed before Auth deletion. Same-session retries join the running request, and interrupted requests resume through a bounded startup/periodic worker without storing ID tokens.

A new job requires verification within five minutes. An already-authorized job can resume using its accepted unexpired session; newer authentication must be recent, and older pre-lock sessions are rejected. Completed records remain at least two hours for confirmation and stale-token protection, then become eligible for automatic pruning. Pending/data-deleted records do not expire automatically. New locks carry `policyVersion: 2`. Remaining legacy pending work adopts preservation; legacy data-deleted/completed work finishes or confirms without replaying cleanup. Previously erased content is never reconstructed. Unsupported policy versions fail closed, including pruning. A persistent deployment floor prevents the old destructive binary from restarting. See [the service implementation and test limits](../../backend/account-deletion/README.md).
