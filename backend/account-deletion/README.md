# Account deletion service

Isolated Node service for Restroom Ready’s native Delete account action. It uses pinned `firebase-admin` **14.5.0**, listens only on **127.0.0.1:3002**, and has no production credentials in this directory. Production now runs behind the existing HTTPS site under a dedicated operating-system account. The least-privilege credential remains outside Git and outside the main web process.

`DELETION_POLICY_VERSION = 3` is deployed as `20261024T023422Z-378edaa8fc9f`, adding paired public-note cleanup, immutable V2 code-report cleanup and versioned code-feedback cleanup while preserving public submitted locations and existing cleanliness ratings anonymously. The persistent startup floor is 3. Source testing and deployed verification are recorded below; native distribution remains a separate gate.

## API

- `GET /health` → `200 {"status":"ok"}`. This checks the running HTTP process, not live Firebase availability.
- `POST /api/account/delete`, `Authorization: Bearer <Firebase ID token>`, `Content-Type: application/json`, body exactly `{}` → `200 {"status":"deleted"}` only after cleanup and Auth deletion are confirmed.
- Origin must be absent (native client) or exactly `https://nyc.imfinethanku.me`. The API accepts no UID or deletion target from the caller. Responses use `Cache-Control: no-store` and fixed error codes; no token, UID, profile or private payload is logged.

New requests need a non-anonymous Google or Apple account, a verified unexpired/unrevoked Firebase ID token, a matching enabled live Auth user and `auth_time` no more than 300 seconds old. The native client reauthenticates the existing account/provider before calling this service. Apple authorization/token revocation belongs to that client flow; this service does not receive Apple authorization codes.

## Cleanup and recovery

An administrator-only `accountDeletionLocks/{uid}` marker is written before cleanup. Deployed client rules must block that account’s private access and authenticated writes whenever the marker exists. No such privileges are granted to a client by this service.

The marker pins the accepted session’s `auth_time` and provider. Same-session calls join the running job; HTTP disconnects do not cancel an authorized deletion. Older pre-lock sessions are rejected. A newer same-account authentication must itself be recent, and becomes the accepted session for later retries. An unexpired token from the originally accepted session can retrieve/resume an existing request after the 300-second new-request window. After Auth is gone, HTTP retry needs a matching `data-deleted` or completed receipt. The private receipt stores no ID token.

Each request has a renewable 90-second lease; shared-data transactions verify its owner and expiry. A startup/30-second recovery worker scans expired leases, at most three 20-document pages per tick and two jobs concurrently. It only resumes already-authorized, valid server-owned pending/data-deleted markers. It cannot create a new deletion request without a fresh verified token. SIGTERM/SIGINT stop accepting HTTP, stop new recovery work and drain current jobs. A forced restart can resume the durable marker.

Cleanup gathers ownership before removing the UID root. It removes this account’s private saved places, notes, codes, checks and receipts recursively; reserved public codes; paired visit reports with exact place/timestamp ownership evidence, and the new paired public notes described below. Other users’ votes, codes, reports, private data and ownership reservations remain. Removing a public-code verification clears only `lastVerifiedAt` when the exact code version and timestamp still match this account’s receipt.

Unified reports use `restroomUnifiedVisits/{placeID}/reports/{reportID}` and private `users/{uid}/restroomReadyUnifiedVisitReceipts/{reportID}` receipts. Each receipt has exactly `placeID`, `submittedAt`, and nullable `codeReportID`. A fenced transaction validates the exact receipt, place and submission timestamp, then removes the public report and receipt together before recursive private cleanup or Auth deletion. Malformed or vanished ownership with remaining public text fails closed. A valid receipt whose public report is already absent can be removed safely. The optional code link never authorizes code deletion: V2 code ownership has its own checked cleanup, and an independently deleted code does not strand a public visit name or comment. Other owners' reports remain byte-for-byte unchanged.

Public text notes use the separate `restroomPublicNotes/{placeID}/notes/{noteID}` namespace, paired with private `users/{uid}/restroomReadyPublicNoteReceipts/{sameID}` records. Cleanup gathers those receipts before deleting private data. Each fenced transaction checks the original receipt, safe place and note IDs, and exact shared submission timestamp, then removes both the owned public note and receipt. An already missing public note allows its valid private receipt to be removed. A malformed or changed receipt, mismatched public place/time, or vanished receipt with public text remaining fails closed with Auth and the pending marker retained for repair. The service never recursively deletes a public note collection and never removes another user's note or imported source comment. No public ownership ID is attached by the note schema. Text deliberately published by a contributor can still contain personal information, so clients must explain that notes are public.

V2 codes use independent immutable reports in `restroomPasscodeReportsV2`, private own records in `restroomReadyPasscodesV2`, and global private `restroomPasscodeV2Owners` reservations. A fenced transaction validates and removes the exact own/public/reservation pair and its feedback summary. An own record without its reservation, a vanished reservation with a remaining code, or mismatched fields fails closed. Feedback receipts in `restroomReadyPasscodeVotes` bind the place, legacy/V2 kind, report ID and exact timestamp version. Before recursive private cleanup, each receipt is removed atomically with a one-vote decrement to its matching same-version `restroomPasscodeFeedback` bucket. Stale versions do not alter newer counts; underflow and malformed ownership fail closed. If this account supplied the exact newest successful-use time, that time becomes unknown rather than guessing another visitor's time. Other code owners and their reports remain unchanged. The private vote key includes place to handle imported legacy IDs reused at different venues.

Public `communityRestrooms/{placeID}` documents remain byte-for-byte unchanged, including original notes, coordinates and dates. Their IDs are `community-` plus independent random 20-character IDs, not UID-derived, and their strict public schema contains no account identity. A transaction verifies the private `restroomSubmissions/{placeID}` receipt’s owner and deletes only that ownership receipt. It adds no public anonymity field, changes no listing timestamp and creates no tombstone.

For every existing own rating, a fenced transaction creates `restroomRatingSummaries/{placeID}/anonymousRatings/{randomID}` and deletes `ratings/{uid}` atomically. The target is a fresh 256-bit cryptographically random ID generated outside the transaction callback; it is create-only and carries only the original valid `stars` and original `updatedAt`. No UID, UID hash, identity field or UID-to-random-ID mapping is retained. The unmatched `anonymousRatings` namespace is denied to all clients by the existing rules, so raw retained votes remain private. A missing source vote on retry is a no-op; interruption, concurrency and restart cannot duplicate its retained contribution.

Rating discovery still lists parent references including missing summary documents, then reads only this account’s UID vote at each parent in bounded batches. Public summary payloads and update times are never written: count, sum and average remain unchanged, even if a summary was already missing or malformed. Other users’ malformed votes remain untouched. An own vote outside the exact two-field 1–5 half-star/timestamp schema fails closed with a pending lock and Auth intact for administrative repair; it is not sanitized, discarded or copied with unknown private fields. Any future aggregate repair **must read both `ratings` and `anonymousRatings`** and validate their actual votes; counting only the remaining UID-owned votes would silently lose anonymous contributions. This service performs no aggregate repair.

New source markers carry `policyVersion: 4`. An untagged, explicit version-1, version-2 or version-3 `pending` marker adopts version 4 and cleans all remaining public-note, unified-visit and V2 code/feedback pairs while preserving public venues and ratings. A supported legacy `data-deleted` or `completed` marker finishes or confirms its existing phase without replaying cleanup, including version 3. Previously erased votes/listing content are never reconstructed or guessed from totals or tombstones. Unsupported policy versions fail closed. Before enabling unified-report writes, deployment must enter deletion maintenance, stop/drain policy 3, deploy policy 4, and raise the persistent startup floor to 4. Earlier policies do not know the unified ownership receipts and could orphan public names or comments; they must never restart once the new writes are enabled. The existing generic deployment/startup guard supports that forward-only floor. New rules and native clients must wait for the updated backend.

After cleanup, `phase: data-deleted` is committed **before** the final Admin Auth deletion. Completion adds `completedAt` and `expiresAt` two hours later. A periodic pruner deletes only completed, expired receipts under a supported policy; unknown-version receipts remain while other eligible candidates can be pruned. Pending/data-deleted markers never expire automatically and must not receive a Firestore TTL policy.

## Runtime configuration

Use Node 22.13 or newer. Set `GOOGLE_APPLICATION_CREDENTIALS` to an absolute path to a private service-account JSON file for exactly `nye-restroom`. The runtime accepts file modes `0600` or `0640` and uses explicit Admin `cert()` initialization at startup. A root-owned `0640` file can be readable only by the dedicated backend group. The service refuses production startup when either Firebase emulator variable is set. Do not enable SDK debug logging or put credentials in repository files, process arguments or logs.

The runtime needs `datastore.entities.get/list/create/update/delete`, `datastore.databases.get` for transactions, and Firebase Auth user get/delete. See [Firestore IAM permissions](https://firebase.google.com/docs/firestore/security/iam). It does not create users, change provider settings, revoke refresh tokens or disable accounts. The test fixtures import emulator users; that test permission is not needed in production.
