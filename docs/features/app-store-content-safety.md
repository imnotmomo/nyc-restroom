# App Store content safety

Status: implemented locally, with actual emulator/SDK regression and independent review; deployment is pending the coordinator's integrated acceptance. No production comments, source material or codes have been removed for this work.

Public browsing remains available without an account. A signed-in Apple or Google account can send a private report from a displayed visitor note/report, imported source comment/research comment, or public entry-code report. The request contains an exact record reference, version, fixed reason and stable UUID, without copied text, a code value or an author identity. Reports are limited to 20 confirmed requests per account per hour; retrying the same confirmed attempt does not consume another slot. The API returns a receipt only after its Firestore transaction commits.

`POST /api/moderation/reports` accepts exactly `kind`, `placeID`, `recordID`, `reason`, `actionId` and a target pin. `public-note` and `unified-visit` use `postedAt` from the original submission timestamp. `legacy-code` and `v2-code` use `postedAt` from the exact code-update timestamp. `source-comment` and `research-comment` instead use `contentHash`, SHA-256 of the exact raw UTF-8 displayed text, without trimming or Unicode normalization. The six fixed reasons are personal information, harassment, sexual content, spam, misleading information and other. A successful response is exactly `{ "status": "received", "reportID": "<same actionId>" }`.

The restricted moderator dashboard adds Reports, with pending/resolved pages and fixed resolution reasons. Moderators can dismiss a report, remove its selected public content, or remove it and suspend the verified contributor. Imported text has no inferred in-app author and cannot produce a suspension. Missing or malformed ownership evidence cannot identify an author for a suspension. A removed public code keeps its owner-private code, immutable ownership reservation and Saved place. Code markers contain only public record IDs and a version, with no account identity or code value. A removed V2 report ID cannot be republished; legacy code editing may publish a genuinely newer version, while its removed version stays blocked. Owners can still hide or delete their personal records after a public projection was removed.

Removing a visitor comment preserves structured observations when present. For a named unified report, removal also changes its opt-in public attribution to Anonymous and clears the name. Dates and observations remain intact. A text-only record is removed with its matching private ownership receipt. Exact target/version checks, immutable public/removal namespaces and stable action receipts prevent duplicate decisions or removal of a changed record. Moderation acts only after an explicit moderator decision; reports do not automatically delete public data.

Firestore rules enforce a first-pass whole-token abusive-phrase filter on new public note/comment text, opted-in public display names, and public code sharing/updating. The filter does not run on private codes, existing reads or owned cleanup. It is not a comprehensive semantic classifier; private reporting and timely human review remain necessary. New restroom requests are reviewed before publication, and approval applies the filter to their public listing text and optional public code. New pending requests must supply the full current queue schema; legacy public location schemas remain readable.

Moderator-controlled server-only contributor suspensions prevent new/changed public ratings, notes, observations, public codes, code feedback and new location requests. Private Saved, browsing, owned cleanup and account deletion remain available. Suspended accounts can still report abuse. `GET /api/moderation/contribution-status` returns only the requesting account's `allowed`/`suspended` projection, with no account ID, reason or moderator identity. It never turns a failed write into a retry or an access grant.

New report/suspension writes fail closed until the account service reports compiled deletion policy 5 and its persistent version floor is at least 5. The account service reads its own protected floor file and returns only version integers through loopback health; the moderation service gains no credential-directory permissions. An already committed action can still return its exact idempotent receipt during a capability outage. Policy 5 retains safety case status while clearing a deleted reporter's UID/fingerprint, and deletes that account's quota/suspension state. Legacy cleanup receipts from policies 1–4 remain supported. Existing minimum audit records are retained for service safety and do not contain report text or code values.

The API uses fresh Firebase bearer authentication, live enabled-provider checks, exact same-origin browser handling (or native requests without an Origin header), bounded JSON and no-store responses. It does not use a browser session cookie as authorization, and does not claim App Check enforcement. Client rules deny every read/write of the private report, quota and suspension collections. Private author ownership is resolved by the server and is never returned in moderator queue DTOs.

## Deployment order

1. Complete independent source/runtime review and record the final source hashes.
2. Use the existing account-deletion maintenance/deployment workflow to drain policy 4, deploy policy 5 and raise the persistent startup floor to 5. Verify compiled/floor health, unauthenticated deletion rejection and no ability to restart an older policy. Do not lower the floor to roll back.
3. Deploy the reviewed 17-file moderator backend package, preserving its existing credential and moderator roster. Verify active release identity and health; no new IAM permission is required.
4. Deploy the additive report-queue index and wait for readiness, then the reviewed rules. Verify anonymous browsing and protected/private boundaries using read-only production probes.
5. Deploy the moderator dashboard/consumer support and privacy copy and the compatible native App Store candidate. Keep any tester-group changes explicit.
6. Verify the live active bundles, real moderator authorization and empty/loading/error states. Use actual reports or isolated demo fixtures for mutations; do not create invented production ratings, notes, locations or codes for QA.

Acceptance evidence is recorded in `app-store-content-safety-qa.json`. The dedicated local demo harness and synthetic fixtures are excluded from the deploy allowlist. Test results are not proof of an end-to-end real-account production deletion or moderation action.
